# Test Design Skill

## Purpose

Спроектировать комплексную тестовую модель (Test Design) на основе требований для обеспечения полного покрытия функционала и импортировать ее в систему управления тестированием.

## Inputs

- Проанализированные требования (бизнес-правила, UI/UX макеты, критерии приемки)
- Сформированные задачи из Jira для привязки тест-кейсов к конкретным задачам (необязательно)
- Ссылка или название проекта в системе управления тестированием
- Шаблон тест-кейса (необязательно)

## Procedure

1. Проанализировать требования с применением техник тест-дизайна:
   - Эквивалентное разбиение (Equivalence Partitioning).
   - Анализ граничных значений (Boundary Value Analysis).
   - Таблицы принятия решений (Decision Table Testing).
   - Переходы состояний (State Transition Testing).
2. Разработать тест-кейсы со следующими полями:
   - **Title** — краткое описание проверки
   - **Pre-conditions** — предусловия
   - **Steps** — шаги выполнения
   - **Expected Result** — ожидаемый проверяемый результат, соответствующий критериям приемки для итога. Если есть Expected Result для промежуточных шагов, добавить их для них.
   - **Priority** (High, Medium, Low) — приоритет согласно требованиям
   - **Type** — тип тестирования (Functional, UI, Integration)
3. Проверить тест-кейсы на дубликаты и совпадения с существующими в системе сценариями и исключить их из списка.
3. Если в блоке Inputs указан шаблон тест-кейса и он содержит дополнительные поля, которых нет в шаге 2, то добавить их.
4. Построить матрицу трассировки (RTM), связывающую каждое Acceptance Criteria с покрывающими его тестовыми сценариями в следующем виде:

| Требование (кратко) | Тестовые сценарии | Покрытие |
|---------------------|-------------------|----------|
| Краткое содержание указанной в требованиях функциональности | TC-01, TC-02 | Full |
| Краткое содержание указанной в требованиях функциональности | TC-03 | Partial |

**Уровни покрытия:**

- **Full**: все аспекты критерия проверены хотя бы одним сценарием.
- **Partial**: критерий проверен частично (указать, какой аспект не покрыт).
- **None**: покрытие отсутствует (указать причину).

5. Создать тестовые кейсы в системе управления тестированием.
6. Сопоставить созданные тест-кейсы с исходными пунктами требований и задачами Jira, если в Inputs указаны задачи.

## Rules

- Тест-кейсы должны быть атомарными, независимыми и воспроизводимыми.
- Обязательное покрытие как позитивных, так и негативных сценариев, а также граничных условий.
- Не создавать дублирующие тест-кейсы.
- Именование тест-кейсов должно отражать суть проверяемой проверки.
- Не додумывать тест-кейсы при недостаточной информации в требованиях.
- Не удалять/не изменять существующие сценарии.

## Output

Отчет о созданных тест-кейсах, содержащий следующие данные:

- Список тестовых сценариев со всеми полями и ссылками на них в Qase
- Матрица трассировки (RTM)
- Список тест-кейсов, которые были исключены из списка

## Completion Criteria

- 100% ключевых бизнес-требований покрыты тест-кейсами.
- Матрица прослеживания (RTM) подтверждает связь каждого требования с минимум одним тест-кейсом.
- Структура полностью подготовлена и импортирована в Qase.
- Отсутствуют дублирующиеся тест-кейсы.
